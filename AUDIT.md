## 1. Stack & how the pieces talk

| Layer | Reality |
|---|---|
| Backend | Laravel (PHP 8.5), `backend/`, API prefix `/api`, served on port 8000 |
| Frontend | React + Vite, `frontend/`, port 3000, talks to `/api` (vite proxy) |
| DB | `SESSION_DRIVER=database`; weddings/guests/users tables (SQLite or MySQL per env) |
| Auth | **Laravel Sanctum in SPA / cookie-session mode** (`statefulApi()`), CSRF-cookie based |
| OpenAI | Plan references `VITE_OPENAI_API_KEY` (frontend) — not yet used in code |

### ⚠ PLAN MISMATCH — auth is cookie/session, not bearer-token
The plan (Phase 1) describes "token-based auth via Sanctum… token attached to
every API call… on 401 redirect." The actual implementation is **Sanctum
stateful SPA mode**: it uses session cookies + a CSRF token, **not** bearer
tokens stored client-side.

- `bootstrap/app.php` calls `$middleware->statefulApi()`.
- `routes/api.php` wraps everything in `Route::middleware('web')` (boots session).
- `frontend/src/lib/api.js` does `fetch(..., { credentials: 'include' })`, first
  hitting `/api/csrf` and echoing the `XSRF-TOKEN` cookie back as `X-XSRF-TOKEN`.

This is a **valid and arguably better** choice for a same-site SPA — but the
plan's "store the token / send it as a header / long-lived token" language does
not apply. The "stay logged in" feature should be done via Laravel's
**remember-me** cookie, which the backend already half-supports (see Phase 1 gaps).

### ⚠ PLAN MISMATCH — role names
Plan says roles are `owner` | `client`. **Code uses `admin` | `customer`**
(`App\Enums\UserRole`). They map 1:1:

| Plan term | Code term |
|---|---|
| Owner | `admin` |
| Client | `customer` |
| Guest | (no account — guest token only) |

The rest of this doc uses the **code** terms (admin/customer) to stay accurate.

## 2. Data model (models + migrations)

Migrations: `backend/database/migrations/`
- `0001_01_01_000000_create_users_table.php` (base Laravel users)
- `2026_06_06_000001_add_role_to_users_and_create_weddings_tables.php`
- `2026_06_06_000002_add_invitation_fields.php`
- `2026_06_08_000003_add_google_maps_url_to_weddings_table.php`

### `users`
- Standard Laravel columns + `role` string (default `customer`).
- `App\Models\User`: casts `role` → `UserRole`, `password` → hashed. Helpers
  `isAdmin()`, `isCustomer()`. Relations: `hasOne(Wedding)` (as owner via
  `user_id`), `hasMany(Wedding, 'created_by')` (weddings this admin created).

### `weddings`
Columns: `id, user_id (owner), created_by (admin), title, slug (unique,
nullable), bride_name, groom_name, event_date, event_time, venue,
venue_address, google_maps_url, template_slug (default 'classic' in migration,
'velvet' in provisioner), message, photos (json), status (default 'draft'),
timestamps`.
- `App\Models\Wedding`: casts `event_date`→date, `photos`→array. Relations:
  `owner()`, `creator()`, `guests()` (ordered by `sort_order`).
- **`status`** is validated as `in:draft,ready,sent` on update — but **nothing in
  the UI ever changes it past `draft`**, so "publish/unpublish" is not wired.
- **No `paid` / payment column exists at all.**
- `slug` column exists and is **unique**, but is **never used for routing** (guests
  are reached by per-guest `token`, not by wedding slug — see §4).

### `guests`
Columns: `id, wedding_id, token (uuid, unique, nullable), name, sort_order,
rsvp_status (nullable string), timestamps`.
- `App\Models\Guest`: belongs to `Wedding`.
- **RSVP is per-guest**: each guest row has its own unique `token` → its own
  invitation link `/invite/<token>`. `rsvp_status` ∈ {null=pending, `attending`,
  `declined`}.
- **No RSVP fields for**: party size / number of guests, meal choice, free-text
  note. **No RSVP deadline** field anywhere.

| GET | `/api/admin/weddings` | `Admin\WeddingController@index` | `auth` + `admin` |

### ⚠ PLAN MISMATCH — `/me` endpoint
Plan says `GET /me`. The actual endpoint is **`GET /api/user`** and it returns
`{ user: null }` for guests rather than 401. It does **not** return the user's
invitation id (frontend fetches `/api/wedding` separately).

### Ownership enforcement — GOOD, server-side
- `app/Http/Middleware/EnsureAdmin.php` (`admin` alias) → 403 for non-admins.
- `app/Policies/WeddingPolicy.php`: `view`/`update` allow admin OR
  `wedding.user_id === user.id`. `WeddingController` and `GuestController` call
  `$this->authorize(...)`, so a customer can only touch their own wedding.
- `WeddingController::resolveWedding()` lets an **admin** target any wedding by
  passing `wedding_id`; a customer always resolves to `user->wedding`. Solid.

### Credential provisioning — EXISTS (`app/Services/CustomerProvisioner.php`)
- Generates `email = strtolower(email_local) . '@' . config('convive.customer_email_domain')`
  (domain default `platform.com`, env `CONVIVE_CUSTOMER_EMAIL_DOMAIN`).
- Generates a random 12-char password via `Str::password(12)`, returns it once.
- Creates the `customer` user + a `draft` wedding in one transaction.
- **⚠ Weak collision handling**: if `email_local` is omitted it falls back to
  `'customer-' . User::where(...)->count() + 1` (relies on PHP 8 precedence; no
  uniqueness guarantee). If the chosen `email_local` already exists, the DB
  unique constraint throws a raw 500 — there is **no "append a number"** retry as
  the plan requires.

## 4. Frontend (router + pages)

Router: `frontend/src/main.jsx` (no `App.jsx`).

| Path | Component | Guard |
|---|---|---|
| `/` | `components/LandingPage.jsx` | public |
| `/invite/:token` | `pages/InvitationPage.jsx` | public |
| `/login` | `pages/LoginPage.jsx` | public |
| `/admin` | `pages/AdminDashboard.jsx` | `ProtectedRoute role="admin"` |
| `/admin/customers/new` | `pages/CreateCustomerPage.jsx` | `ProtectedRoute role="admin"` |
| `/dashboard` | `pages/CustomerDashboard.jsx` | `ProtectedRoute role="customer"` |
| `*` | → redirect `/` | — |

Auth plumbing:
- `context/AuthContext.jsx` — loads `/api/user` on mount, exposes
  `user, loading, login, logout, refresh, isAdmin, isCustomer`.
- `components/ProtectedRoute.jsx` — handles loading, redirects guests to
  `/login`, redirects wrong-role users to their own home. This **is** the
  `RequireAuth` + `RequireRole` the plan asks for (combined).
- `lib/api.js` — central fetch wrapper, CSRF handling, friendly error extraction.
  **Does not special-case 401 → redirect** (relies on ProtectedRoute + `/api/user`
  returning null).

Templates: registered in `lib/templates.js` (6: velvet, sage, azure, andalus-fr,
roseraie, ivoire), rendered via `pages/InvitationPage.jsx` `TEMPLATE_VIEWS`, demo
tokens in `lib/resolveInvitation.js`.
- **Orphan:** `frontend/src/templates/lilyrose/` exists on disk but is **not**
  registered anywhere (not in templates.js, not in TEMPLATE_VIEWS). Either wire
  it up or remove it.
- `dar/` directory backs the `andalus-fr` slug.

## 5. State per actor (what works today)

### Owner / admin
- ✅ Log in, recognised as `admin`, lands on `/admin`.
- ✅ `/admin` lists **guest invitations across all weddings** with RSVP summary
  (accepted/refused/pending) and links. **⚠ It is not a "customer list"** — there
  is no per-customer row, no status/paid column, no search.
- ✅ Create customer (`/admin/customers/new`): name, wedding title, optional
  email-local, template → provisions account + wedding, shows email + password
  **once** (no copy button).
- ❌ View/regenerate credentials later. ❌ Edit/delete/unpublish a customer.
  ❌ Reassign template after creation (from UI). ❌ Mark as paid (no field).
  ❌ Per-customer RSVP drill-down.

### Client / customer
- ✅ Log in, recognised as `customer`, lands on `/dashboard`.
- ✅ Single `CustomerDashboard` page: edit invitation fields (names, date, time,
  venue, address, maps link, message, photo upload up to 6), see RSVP stat
  counts, manage guest list as newline-separated names → generates per-guest
  links, lists those links.
- ❌ Onboarding wizard. ❌ Live preview beside the editor (only a "Preview demo"
  link). ❌ Autosave (manual "Save" buttons; uses `window.alert`-style inline
  message). ❌ In-dashboard template switcher. ❌ Share screen (QR / WhatsApp /
  copy-link button). ❌ CSV export. ❌ Settings / change-password page.
  ❌ Mobile-first treatment (uses `lg:grid-cols-2`, otherwise generic).

### Guest
- ✅ Open `/invite/<token>`, see the template render with their name + wedding
  data; RSVP attending/declined; status persists; admin & customer dashboards
  reflect it.
- ❌ RSVP party size / meal / note. ❌ RSVP deadline enforcement (no field).
- ❌ Add-to-calendar (directions link exists via `google_maps_url`).
- ⚠ No "unpublished" gate: any valid guest token renders regardless of wedding
  `status`. Invalid token → `firstOrFail` 404 → frontend shows "Invitation not
  found." (acceptable, but draft weddings are still publicly viewable by token).

## 8. Decisions from the plan vs. what the code implies

   password, no self-signup/reset. ✅

   "regenerate-only" (option a) path is viable as-is. Confirm we want (a).
3. **Payment** — **no payment column exists**; "manual mark paid" needs a small
   migration. Confirm manual (default) before Phase 2.
4. **One invitation per client** — enforced by `User hasOne Wedding`. ✅
